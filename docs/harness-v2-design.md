# 議事録ハーネス v2 設計（2026-10-25）

対象: PC 内のローカル LLM（Qwen 系 GGUF）で作る議事録。外部 API・クラウド推論は使わない。
評価には完全に架空の会議データだけを使う。

## 0. 方針

- **先にモデル差を測る。** 同じハーネス（v1）でモデルだけを替えて結果を比べ、モデル変更だけで直る問題と、
  ハーネスで直すべき問題を分ける。無条件に全面改修はしない。
- 各段階の出力を検証できる形（JSON の事実・番号付き原文）で持ち、文章化は最後に一度だけ行う。
- 根拠の追跡（どの発言に基づくか）は内部では維持し、**読む人の本文には内部 ID を出さない**。

## 1. 現状（v1）の流れ

1. 入力: メモ（A 系番号）と文字起こし（B 系番号）を文単位に番号付け
2. 事実抽出: 区間ごとに LLM が JSON で事実（種類・話題・本文・根拠番号・担当・期限）を出す
3. 検証: 根拠番号の実在、数字・固有名・否定・条件の一致、決定の判定（DecisionStatus）
4. 統合: 話題ごとにまとめ（Merge）、任意で文章化（FactWriting）、テンプレートへ割り当て
5. 出力: 箇条書き＋〔B012〕形式の根拠番号＋番号付き原文の付録

## 2. v2 の各ステップ

### STEP 1 入力の整理
- あいさつ・相づち・重複発言を「参照用」に分け、事実の根拠には数えない（既存の Uncited 判定を前段に移す）
- メモと発言の対応（同じ内容）を先に結び、片方だけの情報を区別する

### STEP 2 抽出
- 分類を 現状／課題／背景・原因／意見／提案／決定／未決定／Next Action／要確認 に拡張
  （v1 の 情報・意見・質問・提案・決定・作業・未決・要確認 からの対応表を持ち、段階的に移行）
- 1 文に複数の事実がある発言は、根拠番号を共有した複数の事実として出す（例: 「会場は A、予算は 5 万円で決定」→ 決定 2 件）

### STEP 3 話題の統合（最重要）
- 区間をまたいで同じ話題を 1 つにまとめる（現状は区間ごとの話題名が揺れて重複しやすい）
- 統合は「話題名の類似」だけでなく「根拠発言の近さ」「同じ固有名・数字」を使い、LLM には候補の対だけを判定させる
- 統合結果は検証可能（どの事実がどの話題に入ったか）なまま保つ

### STEP 4 根拠の改善
- 決定と提案の区別: 「〜にしましょう」「〜でどうか」は提案、合意の発言（「それで決まり」等）がある場合だけ決定
- 日付候補が複数あるときは矛盾ではなく「候補」として並べる（例: 期限 10/30 または 11/2 ⚠要確認）
- 警告は「読む人が確認すべきもの」に絞り、内部処理の都合（再引用の補正など）はトレース（MinutesTrace）にだけ残す
- **本文に内部参照 ID を出さない**（今回実装、下記）

### STEP 5 構造化出力
会議概要／主要な議題／現状と課題／分析・背景／決定事項／対応方針／Next Action／未決事項・確認事項。
既存の固定セクション形式（FixedSections）を拡張し、各事実の種類から機械的に配置する（LLM に配置させない）。

## 3. 今回の最小実装

`MinutesPresentation.ForReader`（FloatingMemo.Core/Services/Minutes）:
- 生成された議事録の各項目の〔B012・B013〕を Markdown の脚注 `[^1]` に置き換え、脚注に原文の短い引用を入れる
- 同じ根拠は同じ脚注番号を使う。付録にない番号の引用は消さずに残す（情報を失わない）
- 番号付き原文の付録・警告・項目の文言は変えない。評価・品質チェック（MinutesQuality）は従来どおり変換前の文書で行う
- アプリはノートとして保存する直前にだけ適用する。プレビュー表示では脚注として描画される
- テスト: `MinutesPresentationTests`（架空データ、5 件）

## 4. 次の段階（モデル比較の結果を見てから）

1. Qwen3.5-4B / 9B を v1 ハーネスのまま評価（モデル単体と、ハーネス経由の両方）
2. モデル変更で改善しない項目（話題の重複、決定と提案の混同、警告過多）を STEP 3・4 から順に実装
3. 各段階で既存の架空評価セット（EvaluationMeetings ほか）の点数が下がらないことを確認

## 5. ボトルネックの整理（2026-10-26）

指摘された 5 点が、現行コードのどこで起きているか（モデル比較の前に作り直さないための整理）。

| 課題 | 現状の処理 | 原因の見立て | 最初に試す小さな改善 |
|---|---|---|---|
| 1 文に複数の事実 | FactPrompt で 1 回抽出、使われなかった節だけ再抽出（ハーネス v1） | 抽出の指示が「1 文 1 事実」を前提にしている。再抽出は節単位なので「A と B に決定」のような並列は拾えない | 根拠番号を共有した複数事実を明示的に許す指示と、検査（同じ根拠に決定が 2 件あっても重複扱いしない） |
| 話題統合 | Merge（話題名の類似） | 区間ごとに話題名が揺れ、名前だけでは同じ話題と判定できない | 同じ固有名・数字・近い根拠番号を持つ話題を候補にして、統合の可否だけを LLM に聞く（STEP 3） |
| 誤認識の校正 | TranscriptCorrector（辞書で裏付けられた候補だけ適用、他は〔要確認〕） | 辞書にない誤認識は残る。推測で補わない方針は正しい | 校正候補の提示を増やす（適用は従来どおり辞書の裏付けがあるものだけ） |
| 根拠検証 | FactEvidence・DecisionStatus | 提案と決定の境界、日付候補の扱い、警告が内部処理の都合まで出ている | 日付の複数候補を矛盾にしない／警告を読者が確認すべきものに絞る／内部番号は脚注化（実装済み） |
| 文章化 | FactWriting（任意）＋話題ごとの見出し | 事実の列挙が中心で、目的・現状・課題・方針・次のアクションの構成になっていない | 事実の種類から STEP 5 の見出しへ機械的に配置し、文章化は見出しごとに短く |

モデル変更だけで改善する可能性が高いのは「日本語の自然さ」「話題名の揺れ」「1 文の複数事実の取りこぼし」。
ハーネスで直す必要が高いのは「警告の多さ」「日付候補の扱い」「構成（STEP 5）」。モデル比較の結果で優先順位を確定する。
