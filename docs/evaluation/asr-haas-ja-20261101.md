# Haas-ja-v1.0 の検証（2026-11-01）

前回（[asr-model-comparison-20261031.md](asr-model-comparison-20261031.md)）は、公式の実行環境が Linux 限定のため実行できなかった Haas-ja-v1.0 を、speech.cpp（Windows ネイティブ、Vulkan）で検証しました。
評価には前回と同じ架空の会議音声・採点・議事録処理（Qwen3-4B）を使い、Whisper（現行）と Nemotron 3.5 Transcribe と比べました。
本番アプリの設定・既定値・モデルは変えていません。

**結論:**
- Haas-ja は、この PC（RTX 4060 Ti 8GB、Vulkan）で WSL2 なしに動きました。速度とメモリは3つのモデルで最も良い結果でした。
- 文字起こしの精度は Whisper より明らかに高く、Nemotron にわずかに届きませんでした。
- 議事録の重要事項は 99〜102/129 で、Whisper の 75〜76 と Nemotron の 115〜116 の中間でした。
- 差の主な原因は、文末の「。」が抜けて文が連結されることです（6章）。区切りの末尾に「。」を補うと 110/129 に上がりましたが、これは探索的な結果です。
- 次期 ASR の**第一候補**として評価します。ただし、本番に入れる前に、句読点の補い方と短い応答の扱いを開発用データで決める必要があります。

## 2. Vulkan での推論

- `speech devices` で RTX 4060 Ti（Vulkan0、8.6GB）を認識しました。
- WSL2、再起動、ドライバ更新は、どれも不要でした。
- 読み込みは約0.6秒です。音声エンコーダーは GPU で動き、Q8_0 のデコードは既定で CPU で動きます。
- **区切らずに1回で処理する方式には長さの上限があります。** 注意機構が全区間にかかるため、必要なメモリは長さの2乗で増えます。
  - 3分：VRAM 1.5GB
  - 6.4分：VRAM 3.8GB
  - 23.7分：36GB が必要で失敗（`ErrorOutOfDeviceMemory`）
- 公式も、30秒を超える音声は発話区間ごとに処理するよう勧めています。そこで、評価の本命は発話検出（Silero VAD）で区切る方式にしました。

## 3. 条件

| 設定 | 内容 |

- スクリプト：`tests/asr/eval/run_haas.py`、長い音声の作成：`tests/asr/eval/make_long.py`

### 分かったこと

**精度**
- Haas＋語彙の CER は、Whisper（現行）より大きく低くなりました（h01 で 17.7% → 4.8%）。Nemotron（4.1%）には少し届きません。
- 数値は、全会議で Nemotron と同じく全問正解でした。

**カスタム語彙の効果**
- h01 の用語は 11/20 から 17/20 に、h02 は 29/31 から 31/31 に上がりました。読みなし（用語だけ）でも 15/20 でした。3モデルの中で最も効果がありました。
- 一方、「青嶺学院」は語彙を渡しても「聖霊学院／精霊学院」のままでした（3回とも0件）。既存の単語に近い架空の名前には、既定の強さでは効きません。

**区切りによる誤り**
- 最長10秒で区切ると、長い文の途中で切れることがあります。h01 では「過去問は」の途中で切れ、「過去と岩」になりました。
- 最長28秒にしても、全体の精度は上がりませんでした（h01 で 7.3%）。

**短い応答の欠落**
- 区切る方式では、「はい」の欠落が2〜3件ありました（Whisper は0〜1件）。
- 原因は2つが重なったことです。
  - 発話検出が、直前の発言の後0.4秒以内の「はい」を同じ区間にまとめる（無音の判定は500ms）
  - Haas が、区間の末尾にある短い語を出力しない
- 区切らずに処理すると「はい」は残りました。

会議ごとの重要事項（3回の範囲）は次のとおりです。

| 会議 | 正解台本 | Nemotron＋用語指定 | Haas＋語彙 | Haas＋語彙＋「。」（参考） | Whisper（現行） |
|---|---|---|---|---|---|
| h01（19件） | 18 | 15〜18 | 12〜15 | — | 7〜9 |
| h02（24件） | 20〜23 | 20〜22 | 18〜22 | — | 16〜17 |

- **Haas は Whisper より議事録が大きく良くなりました**（重要事項 +23〜26件）。ただし、Nemotron との差は CER の差（4.8% 対 4.1%）より大きくなりました。
- **差の主な原因は句読点です。**
  - Haas は区間の末尾に「。」を付けないことが多くあります。
  - アプリの `JoinSegments` は日本語の区間を区切りなしでつなぐため、「会議を始めます今日は…」「あと二人ですね定員は35人に増やします」のように、文や話者がつながります。
  - その結果、議事録処理が文を正しく分けられなくなります。
- **区切りの末尾に「。」を補う処理を試したところ、99 → 110（雑音なし）、87 → 98（雑音あり）に上がりました。**
  - これは今回見つけた原因を確かめるための探索的な条件です。ホールドアウトで調整した値ではないので、採用の根拠にはしません。
  - 本番に入れる前に、開発用データで補い方を決める必要があります（疑問文の「？」など）。
- **語彙の効果は、議事録では打ち消されました**（102 対 99）。用語の正解は増えましたが、3回の結果のばらつきと「。」の問題のほうが大きく出ています。
- **雑音ありでは句読点の欠けが増え、議事録が下がりました**（87）。

**Haas-ja は「Whisper より高精度」「Nemotron より軽量かつ高速」の両方を満たします。** 次期 ASR の第一候補として評価します。

ただし、議事録の品質ではまだ Nemotron に届きません。本番に入れる前に、次の点を開発用データで確かめる必要があります。
1. 区間の末尾の句読点を補う処理（今回の探索で +11件）
2. 発話検出の設定と、短い応答（「はい」）の扱い。区間の末尾の短い語が消える問題
3. 長い文が10秒で切れる問題（区切り位置の調整、または前後に余白を重ねる処理）
4. 既存の単語に近い架空の名前に、語彙が効かない場合の対処（`keywords_alpha` を開発用データで調整する）
5. アプリへの組み込み方式（speech.cpp の `speech.dll` の C API か、CLI の子プロセスか）と、配布に含める Vulkan ランタイムの確認
